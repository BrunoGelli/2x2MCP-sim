# Realistic MCP flux integration

This directory connects the frozen, validated detector simulation in
`2x2MCP-sim` to MCP production generated by
`BrunoGelli/2x2MCP-PythiaGen`.

The frozen monoenergetic GPS gun under `gun_tests/` is deliberately left
unchanged. It remains the regression source for custom-particle physics,
charge scaling, EDepSim behavior, ROOT→HDF5 conversion, larnd-sim, Flow, and
event-display checks.

The realistic beam workflow is separate:

```text
2x2MCP-PythiaGen
        │
        │ finite Pythia production sample
        ▼
mcp_spectra + aggregate_summary.csv
        │
        ▼
build_pythia_flux_model.py
        │
        │ reusable non-parametric source-flux model
        ▼
flux_model.npz
        │
        ▼
sample_pythia_flux.py
        │
        ├── Pythia beam-frame sampling
        ├── Pythia → 2x2 coordinate rotation
        ├── straight_line_v0 beamline transport
        ├── detector-plane intersection / acceptance
        └── local injection-plane propagation
        │
        ├── *.hepevt
        ├── *.manifest.csv
        ├── *.summary.json
        └── *.mac
        │
        ▼
custom EDepSim
        │
        ▼
existing convert2h5 → larnd-sim → ndlar_flow pipeline
```

The central design principle is that **Pythia defines the production flux,
the generator layer defines sampling/geometry, and EDepSim defines detector
transport**. No one stage should silently absorb another stage's
normalization or efficiency.

---

## Why there are two programs

The first prototype, `prepare_pythia_flux.py`, replayed individual Pythia MCP
rows directly into EDepSim. That was useful while understanding the data
contract, but it has two important shortcomings:

1. it cannot generate more statistically independent detector-MC throws than
   the stored Pythia rows;
2. its first coordinate transform was inferred from the arbitrary `-x`
   frozen test gun and was wrong for the physical NuMI beam convention.

`prepare_pythia_flux.py` is therefore retained only as a **deprecated entry
point that exits with an explanation**.

The supported workflow is now:

```text
build_pythia_flux_model.py    run rarely
sample_pythia_flux.py         run for each detector-MC sample
```

The first program learns a reusable empirical flux model. The second can
draw as many MCP kinematic throws as needed from that model.

Generating more detector-MC throws than the original Pythia row count does
**not** create additional knowledge about the production flux. The source
model uncertainty is still limited by the original Pythia production
statistics. Resampling is used to reduce detector-MC statistical noise.

# 1. Source inputs from 2x2MCP-PythiaGen

`2x2MCP-PythiaGen` writes two logically different products.

## `mcp_summary`

The summary records the normalization and production bookkeeping, including
quantities such as

```text
mcp_mass_GeV
emitter_pdg
production_mode
geometry_id

n_events_generated
n_mcp_total
n_mcp_accepted

sigma_gen_mb
spectra_prescale
```

For production across many files/shards, run the Pythia repository's existing

```bash
scripts/aggregate_outputs.py
```

and keep the resulting aggregate summary CSV. The new flux builder requires
that CSV with

```text
--summary /path/to/aggregate_summary.csv
```

and treats it as the **authoritative normalization input**.

## `mcp_spectra`

The spectrum tree provides the event-level production kinematics. Important
branches include

```text
mcp_mass_GeV
emitter_pdg
production_mode
geometry_id

E_GeV
px_GeV
py_GeV
pz_GeV

theta_x_rad
theta_y_rad

x_at_detector_m
y_at_detector_m
passed_geometry
```

The realistic source-flux model should be built from a Pythia production in
which the spectrum is **not restricted to detector-accepted MCPs**.

The preferred source is therefore a production generated with the equivalent
of

```text
--write-spectra all
```

with a known `spectra_prescale`.

An accepted-only spectrum is already conditioned on the old Pythia detector
acceptance and cannot represent the full source flux. The builder attempts to
recognize this mistake and fails by default. There is an
`--allow-accepted-only-spectra` escape hatch for diagnostics, but it should not
be used for the production source model.

# 2. One model per MCP mass

The first realistic test point is intended to be

```text
m_chi = 20 MeV = 0.020 GeV
```

The model builder selects one mass at a time. This matches the EDepSim
particle configuration, which also uses one MCP mass per run.

The current custom EDepSim MCP uses `G4hIonisation` and deliberately requires

```text
m_chi > 10 MeV
```

so 20 MeV is a convenient first point.

Later, the same procedure can be repeated for every production mass.

---

# 3. All physically open emitters are included

A realistic flux model is **not** built by combining raw Pythia row counts.

The Pythia generator forces exotic decays for statistics, so the number of
stored rows from one emitter is not the physical relative normalization
between emitters.

For a fixed MCP mass, the builder keeps a separate empirical kinematic model
for every supported, kinematically open emitter:

```text
pi0
eta
eta'
rho0
omega
phi
J/psi
```

By default the builder requires every open supported emitter to be present.
A missing emitter is treated as an error unless
`--allow-missing-emitters` is explicitly supplied.

This matters because different parents produce different energy and angular
spectra, and their relative importance changes strongly as `m_chi`
approaches an emitter's kinematic cutoff.

The source model is therefore hierarchical:

```text
choose physical emitter P
        │
        ▼
sample from f_P(E, tx, ty | m_chi)
```

rather than

```text
merge all raw rows
        │
        ▼
sample according to Monte-Carlo row abundance   WRONG
```

# 4. Physical emitter normalization

The flux builder intentionally follows the same normalization convention as

```text
2x2MCP-PythiaGen/scripts/export_toymc_spectra.py
```

and the normalized accepted-yield plots.

For one stored Pythia MCP row, the existing toy-MC convention is

\[
w_i =
N_{\rm POT}\,
S_P\,
{\rm Br}_{\rm exotic}(P,m_\chi,\epsilon)\,
\frac{f_{\rm prescale}}{N_{\rm events,P}}.
\]

The new source model divides out the common factors `N_POT` and
`\epsilon^2`. It is therefore normalized in units of

```text
MCP / POT / epsilon^2
```

and stores a source-row weight proportional to

\[
\widetilde w_i =
S_P\,
\frac{{\rm Br}_{\rm exotic}}{\epsilon^2}\,
\frac{f_{\rm prescale}}{N_{\rm events,P}}.
\]

The total source flux represented by emitter `P` is taken from the aggregate
summary:

\[
\Phi_P =
S_P
\frac{N_{\chi,\rm total}}{N_{\rm events,P}}
\frac{{\rm Br}_{\rm exotic}(P,m_\chi,\epsilon)}{\epsilon^2}.
\]

The physical source mixture is then

\[
P(P\mid m_\chi) =
\frac{\Phi_P}{\sum_Q \Phi_Q}.
\]

Thus:

- the **shape** comes from `mcp_spectra`;
- the **absolute source normalization** comes from `mcp_summary`;
- the emitter mixture is physical, not based on row count.

## Light-meson and charmonium process scales

For light-meson mode,

\[
S_{\rm light}=1.
\]

For the importance-sampled charmonium production,

\[
S_{J/\psi} =
\frac{\langle\sigma_{\rm charmonium}\rangle}
     {\langle\sigma_{\rm SoftQCD}\rangle}.
\]

The builder reads the same `sigma_gen_mb_mean` quantities used by the existing
Pythia post-processing code.

## Exotic branching model

The constants and phase-space approximations in
`build_pythia_flux_model.py` are intentionally synchronized with the current
`export_toymc_spectra.py` implementation.

For a pseudoscalar,

\[
\frac{{\rm Br}_{\rm exotic}}{\epsilon^2}
=
\alpha\,{\rm Br}_{\rm ref}\,(1-4r)^3,
\qquad
r=\frac{m_\chi^2}{m_P^2}.
\]

For a vector,

\[
\frac{{\rm Br}_{\rm exotic}}{\epsilon^2}
=
\alpha\,{\rm Br}_{\rm ref}\,
\sqrt{1-4r}\,(1+2r).
\]

Closed channels receive zero weight.

These are the current model choices inherited from the Pythia-normalization
layer. They are not detector-response parameters.

# 5. Non-parametric kinematic model

The builder does **not** fit an analytic beam formula.

For each emitter it constructs a weighted 3D histogram in

\[
\left(
\log_{10} E,\;
t_x,\;
t_y
\right)
\]

where

\[
t_x = \frac{p_x}{p_z},
\qquad
t_y = \frac{p_y}{p_z}.
\]

These variables are useful because they preserve the joint energy/angular
correlations and are directly related to long-baseline geometric projection.

The default requested binning is

```text
24 bins in log10(E)
28 bins in tx
28 bins in ty
```

with **weighted-quantile bin edges**. Quantile edges avoid spending most bins
in empty tails while preserving rare kinematic regions better than a simple
uniform grid.

The histogram is sparse in practice; only populated cells carry probability.

Sampling proceeds by

1. choosing an emitter from the physical flux fractions;
2. choosing a populated 3D histogram cell according to its flux;
3. sampling uniformly inside that cell;
4. reconstructing the momentum magnitude from `E` and `m_chi`;
5. reconstructing `(px,py,pz)` from `(tx,ty)` with `pz>0`.

This allows arbitrarily many detector-MC throws while retaining the
three-variable Pythia correlations at the histogram resolution.

No claim is made that the interpolated throws contain more production
information than the finite Pythia training sample.

# 8. Coordinate systems

This was deliberately audited before the realistic sampler was finalized.

## Pythia frame

`2x2MCP-PythiaGen` uses

```text
+z = nominal target → detector direction
+x = transverse x
+y = transverse y
```

and requires `pz > 0` for a particle to propagate downstream.

The signed Pythia `x` and `y` conventions are taken to match the signed 2x2
global `x` and `y` conventions.

## 2x2 global beam direction

The official `DUNE/2x2_sim` converter and validation code use approximately

```python
beam_dir = [0.0, -0.05836, 1.0]
```

which corresponds to a beam pointing downward by about 3.34 degrees in the
`y-z` plane.

Therefore there is **no x/z axis permutation**.

The Pythia beam frame is rotated about global `+x`:

\[
R_x(\theta)=
\begin{pmatrix}
1&0&0\\
0&\cos\theta&-\sin\theta\\
0&\sin\theta&\cos\theta
\end{pmatrix},
\]

with

\[
-\tan\theta = -0.05836.
\]

An on-axis Pythia MCP

```text
(0, 0, +1)
```

therefore becomes approximately

```text
(0, -0.0583, +0.9983)
```

in normalized 2x2 global coordinates.

The sampler prints this cross-check every time it runs.

## Why the frozen `(-1,0,0)` gun was still useful

The frozen validation gun

```text
position  = (1.5, -0.2, 0.3) m
direction = (-1, 0, 0)
```

was an intentionally simple transverse test trajectory. It demonstrated that
the full detector pipeline preserves coordinates consistently, but it did
**not** define the physical NuMI beam axis.

That baseline remains valid and unchanged.

# 9. Beam axis position at the detector

The current sampler defaults to

```text
beam axis at detector = (0.0, -0.42, 0.0) m
```

following the `MiniRun5` convention in
`DUNE/2x2_sim/run-genie/flux/GNuMIFlux.xml`, where the beam coordinate is
placed 42 cm below the TPC center.

This is intentionally configurable:

```text
--beam-center-x-m
--beam-center-y-m
--beam-center-z-m
```

because geometry versions can evolve.

The physical target-to-detector baseline defaults to

```text
1040 m
```

matching the Pythia projection convention and the approximately 1.04 km NuMI
baseline.

The Level-0 point target is placed at

\[
\vec r_{\rm target}
=
\vec r_{\rm beam\,center}
-
L\,\hat b.
\]

# 10. Explicit beamline transport layer

The sampler contains a named beamline-transport layer from day one.

For the first implementation the only supported model is

```text
straight_line_v0
```

and this is recorded prominently in every sampling JSON and generated EDepSim
macro.

`straight_line_v0` means:

```text
energy loss             OFF
multiple scattering     OFF
magnetic deflection     OFF
attenuation              OFF
material interactions   OFF

E_out = E_in
p_out = p_in
```

apart from the one fixed Pythia→2x2 coordinate rotation.

This is an intentional **Level-0 beamline model**, not an assertion that the
real NuMI material budget is irrelevant for all MCP charges.

The software ordering is already chosen so a future beamline model can be
inserted without redesigning the source-flux or EDepSim interfaces:

```text
source sampling
    ↓
coordinate rotation
    ↓
beamline transport
    ↓
detector acceptance
    ↓
local injection
```

A future Level-1/Level-2 implementation may add material energy loss,
scattering, magnetic effects, attenuation, or a precomputed beamline response
kernel.

---

# 11. Acceptance is applied after the coordinate rotation and beamline layer

The sampler first rotates a source MCP into the 2x2 global frame and propagates
it from the point target using `straight_line_v0`.

The ray is then intersected with the global detector plane

```text
z = beam_center_z
```

and the first approximate face cut uses

```text
x in [-0.65, -0.05] m
OR
x in [+0.05, +0.65] m

y in [-0.70, +0.70] m
```

These face dimensions come from the existing `2x2MCP-PythiaGen` approximate
2x2 acceptance, but the intersection is now evaluated **after** the real beam
rotation in 2x2 global coordinates.

This ordering is deliberate:

```text
rotation
  → beamline transport
  → detector intersection
  → acceptance
```

rather than applying the old Pythia acceptance before the physical coordinate
conversion.

The old Pythia `n_mcp_accepted` remains useful as a normalization/reference
cross-check, but it is not used to decide which newly sampled events enter
EDepSim.

---

# 12. Local EDepSim injection plane

EDepSim is not asked to transport each MCP through 1040 m of empty geometry.

For a source MCP that passes the Level-0 detector-face cut, the same straight
ray is intersected with a configurable global injection plane upstream of the
detector.

The default is

```text
z_injection = z_detector_plane - 1.5 m
```

controlled by

```text
--injection-upstream-z-m
```

The primary position and momentum at this plane are written to HEPEVT.

Thus the current division is

```text
~1040 m target → local injection    analytical straight_line_v0
local detector/material transport   EDepSim
```

# 13. EDepSim interface

EDepSim already has a native HEPEVT reader with the `pbomb` flavor, so no new
custom EDepSim C++ generator is required.

`sample_pythia_flux.py` writes

```text
vertex x y z t

PDG
px py pz
E
mass
```

into a `.hepevt` file and automatically creates the matching `.mac`.

The generated macro configures

```text
/generator/kinematics/hepevt/flavor pbomb
/generator/kinematics/set hepevt

/generator/position/set free
/generator/time/set free

/generator/count/fixed/number 1
/generator/count/set fixed
```

and keeps

```text
/edep/db/set/requireEventsWithHits false
```

so a detector inefficiency is not silently turned into an event-selection
loss.

# 14. Charge handling

The source flux model is stored **per epsilon^2**.

For fixed `m_chi`, the same sampled kinematics should be reused across detector
charge points:

```text
same HEPEVT sample
    ├── EDepSim q = 0.1 e
    ├── EDepSim q = 0.2 e
    └── EDepSim q = 0.3 e
```

Set the detector charge separately:

```bash
export EDEPSIM_MCP_MASS_MEV=20
export EDEPSIM_MCP_CHARGE=0.3
```

This has two advantages:

1. production kinematics are not unnecessarily regenerated for each charge;
2. charge-dependent detector comparisons use exactly the same input
   trajectories.

The physical production yield for a requested charge is restored later by
multiplying the per-`epsilon^2` flux by the desired `epsilon^2`.

---

# 15. MCP/anti-MCP sign

Pythia distinguishes `chi` and `chibar`.

The current custom EDepSim fork defines one MCP species,

```text
PDG 9000001
```

with one run-wide charge configured by `EDEPSIM_MCP_CHARGE`.

For the present ionization-focused detector model, the flux sampler writes the
single EDepSim MCP species. The source normalization counts MCP particles, not
pairs.

If sign-dependent transport becomes important later, separate MCP/anti-MCP
definitions should be added to EDepSim.

# 17. Sample the first 100 accepted MCPs

After validating the model:

```bash
python generator/sample_pythia_flux.py \
    out/flux_models/mcp_020MeV/flux_model.npz \
    --output-prefix out/generator/mcp_020MeV_seed12345 \
    --n-accepted 100 \
    --seed 12345
```

The sampler uses rejection sampling:

```text
draw physical source MCP
        ↓
rotate to 2x2
        ↓
straight_line_v0
        ↓
detector face cut
        │
        ├── miss → normalization counter only
        └── hit  → HEPEVT
```

It continues until exactly 100 accepted MCPs have been collected.

The vectorized implementation counts source trials only through the 100th
accepted MCP in the final batch, so the recorded acceptance denominator is
consistent with the stopping point.

Outputs:

```text
out/generator/mcp_020MeV_seed12345.hepevt
out/generator/mcp_020MeV_seed12345.manifest.csv
out/generator/mcp_020MeV_seed12345.summary.json
out/generator/mcp_020MeV_seed12345.mac
out/generator/mcp_020MeV_seed12345.sampled_flux.png
```

# 18. Sampling normalization and event weights

Let

\[
\Phi_{\rm source}
\]

be the total model flux per POT per `epsilon^2`.

If the sampler throws

\[
N_{\rm source}
\]

source MCPs and

\[
N_{\rm acc}
\]

pass the Level-0 face cut, it records

\[
A_{\rm L0}
=
\frac{N_{\rm acc}}{N_{\rm source}}
\]

and

\[
\Phi_{\rm acc}
=
\Phi_{\rm source} A_{\rm L0}.
\]

Every accepted event receives the common weight

\[
w_{\rm event}
=
\frac{\Phi_{\rm acc}}{N_{\rm acc}}
\]

in units of

```text
MCP / POT / epsilon^2
```

which is stored in the manifest as

```text
event_weight_per_POT_per_epsilon2
```

For a physical exposure and charge,

\[
N_{\rm expected}
=
N_{\rm POT}\,\epsilon^2
\sum_{\rm selected\ events} w_{\rm event}.
\]

Detector efficiencies can then be measured by following these accepted events
through EDepSim, larnd-sim, and reconstruction.

# 24. Current approximation layers

The realistic chain currently has several deliberately explicit approximation
boundaries.

## Flux interpolation

```text
weighted 3D histogram in logE, tx, ty
uniform sampling within selected histogram cell
```

No analytic flux fit is used.

## Beamline

```text
straight_line_v0
```

No material/magnetic propagation yet.

## Target

```text
point_target_v0
```

The finite target/horn production position is not yet modeled.

## Detector acceptance

The first acceptance is an approximate rectangular 2x2 face with the central
x gap. A later version can replace this with a geometry-derived intersection
without changing the source model.

## EDepSim MCP physics

The current custom MCP is ionization-focused and uses

```text
G4hMultipleScattering
G4hIonisation
```

with the existing >10 MeV mass restriction.

Keeping each approximation named in provenance is intentional.

# 25. Future beamline transport

The software is already organized so the Level-0 model can be replaced.

Possible future progression:

```text
straight_line_v0
        ↓
effective_material_v1
        ↓
dedicated_geant4_beamline_v2
        ↓
precomputed response kernel
```

A more realistic beamline layer may eventually alter

```text
E
direction
survival probability
```

before detector acceptance.

That is why acceptance is deliberately downstream of beamline transport in
the current code even though `straight_line_v0` does not change the MCP.

# 26. Coordinate-regression idea

A future dedicated coordinate regression can inject deterministic noninteracting
geantino trajectories along

```text
+x
+y
+z
NuMI beam direction
```

to inspect the EDepSim geometry directly.

For the full detector-response chain, deterministic charged MCP/muon tracks
are more useful because geantinos do not generate the ionization needed by
larnd-sim.

This is not required for the first flux-model milestone because the sampler
already prints the nominal-axis transform and the first realistic ROOT sample

# 27. Production principle

The full future efficiency bookkeeping should remain conceptually separated:

```text
Pythia production / normalization
        ↓
source flux model

beamline propagation
        ↓
straight_line_v0 for now

geometric acceptance
        ↓
sample_pythia_flux.py

local material / detector response
        ↓
EDepSim

charge readout simulation
        ↓
larnd-sim

reconstruction / selection
        ↓
ndlar_flow / analysis
```

The final expected yield should be built from these explicit stages rather
than inferred from the number of events that survive the end of the chain.

That separation is the reason this generator layer exists.
